Selected work

Owning a frontend platform

Architecture
Problem
A multi-tenant enterprise product accumulates frontend decisions faster than anyone reviews them. Without a single owner, each team solves bundling, state and permissions slightly differently, and the cost surfaces years later as a codebase nobody can move.
Approach
Be the decision-maker rather than the reviewer. Set the architecture, the Webpack bundling strategy and the engineering standards for performance, accessibility and code quality — then enforce them through review and hands-on work rather than documents. Module Federation where independent deployment earns its complexity, and a boring shared component layer everywhere else.
Result
Six years as the frontend authority on a product used by global customers, with engineering standards that outlast any individual feature — and 3–5 engineers carrying those standards forward through code review and design discussion.

RBAC and secure UI workflows

Security
Problem
In a multi-tenant security product, permissions aren't a feature — they're the substrate. Every screen has to answer "may this user see this, for this tenant, right now", and getting it wrong is a security incident rather than a bug report.
Approach
Model permissions as a first-class part of the frontend architecture instead of scattered conditionals: enterprise-grade RBAC, cookie-based authentication, and secure UI workflows designed with the backend and security teams rather than bolted on after.
Result
Permission logic that is auditable in one place, which is the only version of this that survives a security review.

Legacy modernisation and performance

Performance
Problem
An enterprise dashboard that has grown for years carries weight nobody chose: stale dependencies, a bundle that ships everything to everyone, and load times that quietly erode how often people use the product.
Approach
Attack it from the build inward — Webpack optimisation, bundle splitting, tree-shaking and dependency cleanup — then from the runtime outward with lazy loading, optimised data-fetching and continuous bundle analysis. Most of the weight is decided in a layout long before it reaches a config file.
Result
Build times down 30%. That number compounds in a way user-facing metrics don't — it is paid back on every push, by every engineer, on every CI run, for as long as the project lives.

How I work

  1. Ownership means deciding, not reviewing.

    A frontend owner who only comments on pull requests isn't one. The architecture, the build strategy and the standards have to be someone's call, and then that person has to live in the code.

  2. Performance is a design problem before it's an engineering one.

    Most of the weight I've removed from a bundle was decided in a layout, not in a Webpack config. The engineering part is usually the last twenty percent.

  3. An interface should admit what it doesn't know.

    A visible staleness indicator beats a confident wrong number every time. That matters more in software controlling physical doors, but it is never not true.

  4. Build for the engineers who come after you.

    Component APIs, tooling and standards are the parts of the job with compounding returns. They are also the parts most easily deferred forever.
