SEC 02 // Selected work

Owning a frontend platform

Problem

A multi-tenant enterprise product accumulates frontend decisions faster than anyone reviews them. Without a single owner, each team solves bundling, state and permissions slightly differently.

Approach

Be the decision-maker rather than the reviewer. Set the architecture, the Webpack strategy and the standards — then enforce them through review and hands-on work rather than documents.

Result

Six years as the frontend authority on a product used by global customers, and 3–5 engineers carrying those standards forward.

RBAC & secure UI

Problem

In a multi-tenant security product, permissions aren't a feature — they're the substrate. Getting one wrong is an incident, not a bug report.

Approach

Model permissions as a first-class part of the architecture instead of scattered conditionals: enterprise RBAC, cookie-based auth, secure workflows designed with the security team rather than bolted on after.

Result

Permission logic auditable in one place — the only version of this that survives a security review.

Legacy modernisation

Problem

An enterprise dashboard grown over years carries weight nobody chose: stale dependencies, a bundle that ships everything to everyone.

Approach

From the build inward — Webpack optimisation, bundle splitting, tree-shaking, dependency cleanup — then from the runtime outward with lazy loading and continuous bundle analysis.

Result

Build times down 30%. It compounds in a way user-facing metrics don't — repaid on every push, by every engineer, for the life of the project.

SEC 03 // How I work

01

Ownership means deciding, not reviewing.

A frontend owner who only comments on pull requests isn't one. The architecture, the build strategy and the standards have to be someone's call — and then that person has to live in the code.

02

Performance is a design problem first.

Most of the weight I've removed from a bundle was decided in a layout, not in a Webpack config. The engineering part is usually the last twenty percent.

03

An interface should admit what it doesn't know.

A visible staleness indicator beats a confident wrong number every time. That matters more in software controlling physical doors, but it is never not true.

04

Build for the engineers who come after you.

Component APIs, tooling and standards are the parts of the job with compounding returns. They are also the parts most easily deferred forever.
